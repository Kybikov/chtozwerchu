# Повні треки: стан інтеграції, 3 листопада 2026

Діючий адаптер гри використовує підключення Deezer для синхронізованого
тексту та точних міток слів. Звук — публічне прев’ю або власний аудіофайл.
Повне відтворення через обліковий запис провайдера ще не реалізоване.

Перевірено поточну реалізацію WTBackend `internal/domain/musicmirror` та
доступні маршрути WTAdmin `music`. Deezer Pipe там працює з бібліотекою;
код явно не читає поля відтворення чи завантаження. Поточні підключення
Deezer та Spotify мають статус connected, але цей статус підтверджує
підключення бібліотеки, а не готовий програвач у грі. Секрети для цього
аудиту не експортувалися, підключення й бібліотеки не змінювалися.

Spotify має [Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk),
але [Developer Policy, розділ III](https://developer.spotify.com/policy)
виключає ігри, включно з вікторинами, та інтеграцію з потоками іншого сервісу.
Тому звичайний Spotify SDK не обраний як основа цієї гри. Публічну сторінку
документації Deezer SDK під час перевірки відкрити не вдалося; придатність
окремого SDK або партнерського доступу залишається непідтвердженою.

Повторна перевірка порталу 3 листопада повернула сторінку входу замість
документації API. [Офіційний приклад Deezer](https://github.com/deezer/javascript-samples/blob/master/player_basic.html)
ініціалізує SDK через appId та channelUrl; він не підтверджує працездатність
цього SDK у поточному браузері з нашою сесією WTAdmin. Новий шлях повного
відтворення за цим прикладом не оголошено готовим і не опубліковано.

Користувач підтвердив 3 листопада, що окремого доступу Deezer SDK або
партнерського відтворення наразі немає. Не вважати ARL або успішне читання тексту
підтвердженням працездатності повного аудіо. Мета повного відтворення
залишається відкритою; редактор фрагментів 1.15 її не закриває.

Повторний аудит під час 1.25: через підключений WTAdmin прочитано поточні
`music/accounts` і `music/providers`, без експорту секретів. Deezer має
connected, desktop_browser та library:true; режим описаний як ARL для
сучасного Pipe API і читання плейлистів. У розділі `music` перелічено
27 маршрутів облікових записів, бібліотек і перенесення, без маршруту
повного відтворення. Поточний `deezer_pipe.go` також прямо обмежує
адаптер бібліотекою й не читає playback/media/download.
Посилання API з [порталу Deezer](https://developers.deezer.com/) знову
перенаправило на login; робочий повний програвач з наявною сесією
не підтверджений. [Пакети власної музики 1.25](release-1.25.md) дають
перенесення підготовок між пристроями й не закривають цю вимогу.

## Поточний вебплеєр Deezer

3 листопада окремо завантажено публічні скрипти офіційної сторінки
`https://www.deezer.com/us/channels/explore`, без сесії чи секретів.
Скрипт `app-web.436877b38fb06cd2d227.js` має SHA-256
`56c915c3b77c6423f194d18173e442b88c46dd1a69a3f2793dbec673491d57b5`.
У точному діапазоні UTF-16 3134427–3140162 міститься модуль `bmsN`.
Він будує запит `/v1/get_url` з ліцензійним токеном і токенами треків;
для прев’ю вибирає `PREVIEW / NONE / MP3_128`, для повного аудіо —
`FULL / BF_CBC_STRIPE`. Отже, цей код не є готовим шляхом до звичайного
повного MP3 для HTMLAudioElement. Сам факт наявності ARL не доводить
придатності такого відтворення у грі.

REA прочитала виділений модуль як неактивний текст: Evidence
`ev_10cb5285f21fad2f5a4a2252a238568f31df251a4930bee107a71df277a2dbaa`.
Повний аналіз чотиримегабайтного bundle був обмежений пам’яттю;
виділений модуль розібрано без помилок. Динамічні залежності та runtime
залишаються неперевіреними. Це статичне спостереження поточного модуля,
а не висновок про всі можливі SDK, партнерські чи офіційні вбудовані
програвачі. Медіазапити з приватним токеном не виконувалися, захищені
потоки не завантажувалися й не розшифровувалися. Вихідні скрипти,
походження діапазону та повний Evidence збережено локально в
проігнорованому `output`; у репозиторій вони не входять.
